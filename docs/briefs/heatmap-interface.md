# Heatmap interface (signed 2026-09-04, revised explorer drill)

Tables: `client_company(company_id PK)`,
`company_activation(company_id PK, activated_at, activation_week)`,
`company_week_value(company_id, week_start PK, had_value, had_sync, had_recon)`,
`retention_cells(cohort_week, rel_week 0..8 PK, cohort_size, retained_count)`,
`company_profile(company_id PK, company_name, signed_up_at, activated_at, activation_week, first_upload_at, first_ready_at, first_sync_at, first_recon_at, last_action_at, action_count, active_weeks, path_had_upload, path_had_ready, path_had_sync, path_had_recon)`,
`company_week_action(company_id, week_start PK, action_count, upload_count, txn_count, ap_count, sync_count, recon_count, other_action_count)`.
Week = `date_trunc('week', event_time AT TIME ZONE 'Asia/Kolkata')` Monday; activation = first Accounting Sync with non-null company_id; value = Accounting Sync OR Recon Processed; null company_id excluded; display name = latest `properties->>'companyName'` stored in `company_profile.company_name`.
Refresh: `python -m metrics refresh` or `SELECT * FROM public.refresh_retention('public.events')` (idempotent, rebuilds all six tables from public.events, client companies only). Production hourly ingest is Edge Function `sync-incremental` (see `docs/specs/2026-09-05-supabase-incremental.md`); dashboards still never call Mixpanel.
Staff note: a client company has >= 1 non-staff email; staff-only companies are out of every derived table; staff emails never appear in API people payloads.
Action note: actions = Upload, Mapping/Saved-Template, Invoice/AP (Created, Bulk Edited, Download-Inv, Preview), Txn (Ledger Updated, Status, Type Updated, Config Edited, Vendor Mismatch), Accounting Sync, Recon Processed, Entity/ Delete/Download/Export. Login, Sign Up, Dashboard Viewed, chrome/billing/phone/company events are NOT actions and never enter by_event totals (they may appear in the timeline log).
API: `GET /api/summary` -> page-level Retention cards {client_companies, activated, activation_rate, median_ttv_hours (percentile_cont 0.5 of first_sync_at - signed_up_at hours on company_profile), week8_cohort_week, week8_cohort_size, week8_retained, week8_retention (latest cohort whose W+8 calendar week has fully elapsed; not a matrix average and not an in-progress cell), recon_count, recon_among_activated}; `GET /api/heatmap` -> [{cohort_week, rel_week, cohort_size, retained_count, rate}] (includes Week 0 when its calendar week has started, and Weeks 1–8 only after the observation week has fully elapsed); `GET /api/heatmap/cell?cohort_week=YYYY-MM-DD&rel_week=8` -> {cohort_week, rel_week, people_count, company_count (= retained_count), median_actions_that_week, share_with_upload, share_with_sync, share_with_recon (0-1 fractions over cell companies), users: [{email, distinct_id, user_id, signed_up_at (min Sign Up else first event), last_action_at, lifetime_actions, active_weeks, actions_per_active_week, actions_that_week, companies: [{company_id, company_name, signed_up_at, activated_at, last_action_at, lifetime_actions, active_weeks, actions_per_active_week, actions_that_week (week_action at activation_week + rel*7, missing -> 0), upload_that_week, txn_that_week, sync_that_week, recon_that_week, path_had_upload, path_had_ready, path_had_sync, path_had_recon, ttv_hours (first_sync - signed_up, null if missing), value_events}]}]}; `GET /api/companies/:company_id/summary` -> profile fields + activation_week + ttv_hours + step durations (hours_signup_to_upload, hours_upload_to_ready, hours_ready_to_sync, hours_sync_to_recon, one decimal and null when timestamps are missing or out of order) + last_sync_at/last_recon_at + hours_since_last_sync/hours_since_last_recon + path_type (`ap`, `txn`, `both`, or `neither`) + last_value_week_start/last_value_rel_week + week8_counted (null until activation W+8 fully elapses, otherwise boolean) + path flags + by_week [{week_start, action_count, upload_count, txn_count, ap_count, sync_count, recon_count}] + by_event [{event_name, count}] (actions only, desc, cap 40); `GET /api/companies/:company_id/timeline?limit=100&offset=0` (default 100, max 500 clamped, newest first) -> {total, limit, offset, events: [{event_time, event_name}]}, no email; `GET /health` -> {ok:true}.
API filter addition: `/api/summary` and `/api/heatmap` accept optional inclusive `from_week` and `to_week` bounds in `YYYY-MM-DD`; each bound snaps to its IST Monday, reversed snapped bounds return 400, and summary always includes `cohort_weeks`, the full oldest-first catalog of started Week-0 Mondays, regardless of the selected bounds. The filter clips heatmap rows and the mature Week-8 summary cohort only; lifetime KPIs remain unfiltered.
UI `ui-design/` is the live Retention page (Codex HTML), served by `PORT=4831 python -m metrics.api`. `web/` is the older explorer (may still be on 4830). Dashboards read only these paths; no export clients; no SQL in browser.
